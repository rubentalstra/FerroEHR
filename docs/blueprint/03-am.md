# Blueprint 3 — AM (Archetype Model)

Scope: the archetype/template **constraint semantics** a CDR must enforce on
committed data — cardinality, occurrences, existence, value constraints,
slots, terminology bindings — per AOM 1.4 + AOM 2, ADL, and OPT.
Oracle: `docs/specs/openehr/AM/docs/` (AOM1.4, ADL1.4, AOM2, ADL2, OPT2,
UML/classes) + the AM Release-1.4 XSD closure vendored at
`crates/openehr-its/schemas/xml/components/AM/Release-1.4/` (the *only*
machine-normative definition of OPT 1.4 — there is no OPT 1.4 prose chapter;
see §Spec defects). Pins: AM 1.4.0 + 2.4.0 (`docs/VERSIONS.md`). The CDR's
Stage-1 ingestion format is OPT 1.4 XML; ADL2/AOM2 are cited where they are
the only place a semantic is formalized.

Citation shorthand: `AOM14/04` = `AM/docs/AOM1.4/master04-constraint_model_package.adoc`;
`cADL` = `AM/docs/ADL1.4/master05-cadl.adoc`; `UML:<x>` =
`AM/docs/UML/classes/org.openehr.am.aom14.<x>.adoc`; `AOM2/08` =
`AM/docs/AOM2/master08-validation.adoc`; etc. Line numbers are into the
vendored files.

## Normative requirements (what a compliant CDR MUST do)

### A. The constraint tree and the conformance function

1. **Model the archetype as the C_COMPLEX_OBJECT / C_ATTRIBUTE alternation.**
   An archetype definition is a `C_COMPLEX_OBJECT` (with `rm_type_name`)
   whose `attributes: List<C_ATTRIBUTE>` constrain RM properties, each in
   turn holding child `C_OBJECT`s — recursively down to `C_PRIMITIVE_OBJECT`
   leaves. (AOM14/04 §Overview lines 5–7, §Complex Objects line 70.)
2. **Implement the recursive `valid_value` conformance cascade.** "The
   `valid_value` function tests a reference model object for conformance to
   the archetype … designed for recursive implementation in which a call …
   at the top of the archetype definition would cause a cascade of calls down
   the tree. This function is the key function of an 'archetype-enabled
   kernel' component that can perform runtime data validation based on an
   archetype definition." (AOM14/04 §Valid_value lines 60–62.) This is the
   CDR's core commit-time duty.
3. **Node identification:** every addressable object node carries a
   `node_id` (at-code) that (a) guarantees sibling-node unique
   identification and (b) is a term code defined in the archetype
   ontology/terminology; nodes under a container `C_ATTRIBUTE` must have
   one. Paths are the Xpath-subset archetype paths built from
   `rm_attribute_name` + `[node_id]`. (UML:c_object node_id row lines 26–29;
   AOM14/04 §Node_id and Paths lines 39–44.)

### B. Existence (attribute presence)

4. **Enforce `C_ATTRIBUTE.existence` on every constrained attribute.**
   "An `existence` constraint indicates whether an object will be found in a
   given attribute field … existence is always required" — distinct from
   cardinality (container membership) and occurrences (per-object count).
   (AOM14/04 line 33.) Legal values `{0}`, `{0..0}`, `{0..1}`, `{1}`,
   `{1..1}`; **default when unstated is `{1..1}`** (cADL §Existence
   line 210). `{0}`/`{0..0}` means the attribute must *not* be present
   (cADL line 210). Invariant `Existence_set: existence.lower >= 0 and
   existence.upper <= 1` (UML:c_attribute line 44). For container
   attributes, existence governs presence of the whole container; an
   existence-optional container that is present may still be empty if its
   cardinality allows 0 (cADL lines 205, 275–280).

### C. Cardinality (container membership)

5. **Enforce `C_MULTIPLE_ATTRIBUTE.cardinality` on container values:** the
   member count of the container must lie in `cardinality.interval`;
   `is_ordered` / `is_unique` express list/set/bag semantics ("The
   cardinality cannot contradict the cardinality of the corresponding
   attribute within the relevant reference model", UML:cardinality line 9;
   cADL §Cardinality lines 245–273). **There is no default cardinality** —
   absence of a cardinality constraint means the attribute is treated as
   single-valued, "even for smarter parsers that can access the reference
   model" (cADL line 273). Existence and cardinality may co-occur
   (cADL lines 275–280).
6. **Single-valued attribute with multiple child objects = alternatives:**
   exactly one instance appears in data and it must match *one of* the
   sibling constraint blocks (cADL §Single-valued Attributes lines 214–237,
   principle line 236–237). This includes joint/covariant matching of a whole
   block (e.g. the mph-vs-km/h `DV_QUANTITY` example, lines 218–231).

### D. Occurrences (per-object-block count)

7. **Enforce `C_OBJECT.occurrences`:** how many instances conforming to a
   given constraint block may occur under the owning attribute. Significant
   for children of container attributes (but legal anywhere); "Upper limit
   can only be greater than 1 if owning attribute has a cardinality of more
   than 1" (UML:c_object line 24). `{0..0}`/`{0}` prohibits the node;
   **default when unstated is `{1..1}`** (cADL §Occurrences line 316).
8. **VCOC (archetype-internal validity, enforce at ingestion):**
   "cardinality/occurrences validity: the interval represented by: (the sum
   of all occurrences minimum values) .. (the sum of all occurrences maximum
   values) must be inside the interval of the cardinality." (cADL line 324;
   restated as **VACMCO** in AOM2/08 line 112.)

### E. Open constraints

9. **Honor `any_allowed` / `matches {*}`:** any value permitted by the RM is
   permitted by the archetype; the only residual checks are the stated
   existence bound and, for a type-anchored `*`, that the instance is of the
   named RM type ("the `value` property … must be of type `QUANTITY`, but
   can have any value internally", cADL §"Any" Constraints lines 326–351).
   `C_ATTRIBUTE.any_allowed ⇔ children Void/empty`; invariant
   `Children_validity: any_allowed xor children /= Void` (UML:c_attribute
   lines 34–38, 47).

### F. Value (leaf) constraints

10. **Primitive constraints** (cADL §Constraints on Primitive Types
    lines 645–1006 + UML:c_string/c_integer/c_real/c_boolean/c_date/…):
    - `C_STRING`: value list and/or PERL-syntax regex `pattern`; `list_open`
      marks a non-exhaustive list (UML:c_string).
    - `C_INTEGER`/`C_REAL`: value list or interval.
    - `C_BOOLEAN`: `true_valid`/`false_valid`.
    - `C_DATE`/`C_TIME`/`C_DATE_TIME`: ISO-8601 field patterns built from
      `yyyy-mm-ddThh:mm:ss` with `?` (optional) / `X` (prohibited) per field
      — with the validity rules "where `??` appears in a field, only `??` or
      `XX` can appear in fields to the right; where `XX` appears … only `XX`
      … to the right" (cADL lines 858–861, pattern tables 865–906);
      timezone-required suffix patterns (`±hh`, `±hh:mm`, `±hhmm`, `Z`);
      absence of a timezone constraint means timezone optional (line 910);
      plus literal lists and intervals incl. one-sided (`|< 09:30:00|`,
      lines 914–932; both endpoints of a two-sided interval must agree on
      timezone presence, line 932).
    - `C_DURATION`: designator patterns (`PWD`, `PThm`, …; openEHR
      deviation: `W` combinable with other designators, line 940), value
      lists/intervals incl. negative durations, and mixed
      `pattern '/' interval` form (lines 934–987).
    - Lists of primitives under `cardinality`: every member must match the
      value constraint (lines 989–1005).
11. **openEHR-profile domain types (`C_DOMAIN_TYPE`, what OPT 1.4 actually
    carries):**
    - `C_DV_QUANTITY`: `property` (physical property of all allowed values)
      + `C_QUANTITY_ITEM` list, each pairing one `units` with its own
      magnitude/precision interval — units↔magnitude covariance
      (UML:c_quantity, UML:c_quantity_item; `ADL1.4/master09-customising_adl.adoc`).
    - `C_DV_ORDINAL`: `ORDINAL {symbol: CODE_PHRASE, value: Integer}` list —
      the *(symbol, value)* pair must match one entry (UML:c_ordinal,
      UML:ordinal).
    - `C_CODE_PHRASE`/`C_CODED_TEXT`: `terminology` + optional `code_list`;
      "No list means any code from the terminology is allowed"
      (UML:c_coded_text lines 19–26).
    - `C_DV_STATE`: state-machine constraint (XSD `OpenehrProfile.xsd`).
12. **Assumed values are metadata, not data constraints:** definable on
    primitive leaves only; "default values do appear in data, while assumed
    values don't" (AOM14/04 §Assumed_value lines 54–58; cADL §Assumed Values
    lines 1007–1022). A CDR must *preserve* them through ingestion (clients
    read them) but must not require or inject them at validation.

### G. Slots, internal refs, placeholder constraints

13. **`ARCHETYPE_SLOT` (`allow_archetype` + `include`/`exclude` assertion
    lists):** content filling a slot must satisfy the slot's assertions
    (typically regexes over `archetype_id/value`), and the slot's declared
    RM type and occurrences still apply (cADL §Archetype Slots lines
    535–601; AOM14/04 §Reference Objects line 83). In a *fully flattened*
    OPT, filled slots are replaced by inline copies and closed slots removed
    (OPT2/master03 lines 42–44) — but a slot left open in an OPT still
    constrains what may be committed at that position.
14. **`ARCHETYPE_INTERNAL_REF` (`use_node`):** re-use of a constraint
    defined elsewhere in the archetype; in an OPT these are "replaced by an
    inline copy of the target structure" (cADL §Internal References/§Mixed
    Structures lines 618–643; OPT2/master03 line 41).
15. **`CONSTRAINT_REF` / ac-code placeholders:** a proxy for an externally
    defined value set; the archetype stores only the `acNNNN` code, bound in
    the ontology to external query/value-set identifiers (cADL §Placeholder
    Constraints lines 603–616; AOM14/04 lines 85–91). A CDR that cannot
    evaluate the external resource must at minimum not mis-reject
    (open-constraint semantics) and should record the decision.

### H. Terminology (ontology) and bindings

16. **Archetype ontology integrity:** every at-code used as a `node_id` and
    every ac-code must be defined in the ontology, per language; term
    definitions carry at least `text` + `description`
    (`AOM14/master07-ontology_package.adoc` lines 11–16, 30–32).
    Specialised-code depth discipline (`at0001.0.1` etc., lines 20–28).
17. **Term/constraint bindings:** optional binding sets map at-codes to
    external terminology codes and ac-codes to external value-set/query ids
    (AOM14/07 lines 15–16). AOM2 formalizes the ingestion-side validity
    rules a CDR should apply to uploaded artefacts: **VTTBK** (every term
    binding targets a defined at-code or valid flat path), **VTCBK** (every
    constraint binding targets a defined ac-code), **VTVSID/VTVSMD/VTVSUQ**
    (value-set id/members defined, members unique), **VTSD** (code
    specialisation level), **VTLC** (all codes exist in all languages)
    (`AOM2/master07-terminology_package.adoc` §Validity Rules lines 57–81;
    also AOM2/08 lines 44–47).

### I. Templates and OPT semantics

18. **Templates are specialised archetypes and cannot widen constraints:**
    "all data created due to the use of templates are guaranteed to conform
    to the referenced archetypes, as well as the underlying reference
    model." Templates typically fill slots, apply `{0..0}` to remove and
    `{1..1}` to mandate elements, set default values, and add terminology
    bindings (`AOM2/master10-templates.adoc` lines 5–19).
19. **OPT = fully flattened, resolved artefact:** archetype references
    resolved to full 3-part-version ids; `use_node` refs and slot fillers
    inlined; closed slots removed; **deleted nodes removed** ("attribute
    (`C_ATTRIBUTE`) nodes that have `existence matches {0}` and object
    (`C_OBJECT`) nodes with `occurrences matches {0}`"); component
    archetype terminologies gathered under `component_terminologies`
    (`OPT2/master03-opt_raw.adoc` lines 3, 30–50). The OPT 1.4 XML shape
    itself is normatively the `Template.xsd`→`OpenehrProfile.xsd`→
    `Archetype.xsd` closure (vendored under
    `crates/openehr-its/schemas/xml/components/AM/Release-1.4/`).
20. **Artefact validity at ingestion (AOM2/08, the only formalized
    catalogue):** a CDR accepting uploaded artefacts should apply the
    phase-1/2/3-style checks relevant to a standalone flat OPT — RM
    type/attribute existence (**VCORM/VCARM**), `existence` valid w.r.t. RM
    (**VCAEX**), `cardinality` valid w.r.t. RM (**VCACA**), attribute -arity
    mismatch (**VCAM**), occurrences-vs-cardinality (**VACMCO**), codes
    defined in terminology (**VATID/VATCV**), language/translation
    consistency (**VOLT/VOTM**) (`AOM2/master08-validation.adoc` lines
    26–47, 70–75, 107–112).

## Spec defects/TBDs encountered (verbatim, cited)

1. **OPT 1.4 has no normative prose chapter.** The AM docs carry AOM 1.4,
   ADL 1.4, AOM2, ADL2 and *OPT2* only; OPT 1.4 semantics must be assembled
   from the Template XSD closure + AOM 1.4 + (by analogy) OPT2's flattening
   rules (`OPT2/master03-opt_raw.adoc`). Underdetermined by design.
2. **`CARDINALITY.is_set` documented as a bag** (copy-paste defect):
   "*is_set* (): … True if the semantics of this cardinality represent a
   **bag**, i.e. unordered, non-unique membership." — identical wording to
   `is_bag`. (`UML/classes/org.openehr.am.aom14.cardinality.adoc` lines
   31–41.)
3. **Typo in `C_ATTRIBUTE.any_allowed`:** "True if any value (i.e. instance)
   of the reference model attribute represented by this **C_ATTIRBUTE** is
   allowed." (`UML/classes/org.openehr.am.aom14.c_attribute.adoc` line 38.)
4. **`C_CODED_TEXT.reference` has an empty Meaning cell** — an attribute
   with no documented semantics.
   (`UML/classes/org.openehr.am.aom14.c_coded_text.adoc` lines 27–29.)
5. **Duplicated sentence in cADL §Occurrences:** "In the example below,
   three `EVENT` constraints are shown…" appears verbatim twice
   (`ADL1.4/master05-cadl.adoc` lines 284 and 286).
6. **Unbalanced parenthesis in `C_OBJECT.occurrences`:** "Upper limit can
   only be greater than 1 if owning attribute has a cardinality of more than
   1)." (`UML/classes/org.openehr.am.aom14.c_object.adoc` line 24.)
7. **Timezone prohibition inexpressible (acknowledged):** "NOTE: there is no
   way to state that timezone information be _prohibited_."
   (`ADL1.4/master05-cadl.adoc` line 854.)
8. **Typo + duplicate code in AOM2 validation catalogue:** "for each
   language, ensure that annotations paths are **valida** (VRANP)"
   (`AOM2/master08-validation.adoc` line 61); **VTSD** is listed under both
   "validate terminology code formats" (line 44) and "check that all codes
   mentioned in `definition` are defined in terminology" (line 56).
9. **AOM 1.4 is silent on extra/unmatched instance content.** Only the
   positive `valid_value` cascade is normative (AOM14/04 lines 60–62); no
   rule for rejecting unconstrained siblings exists in AOM 1.4/ADL 1.4 text —
   closure semantics appear first in AOM2 (`c_conforms_to`, VSONCT/VSONCO,
   AOM2/08 lines 96–101). Recorded as decision point F-07-05.
10. **No tuple constraints in AOM 1.4:** covariant leaf constraints
    (units↔magnitude) exist only via the openEHR-profile `C_QUANTITY_ITEM`
    list or alternative blocks; `C_ATTRIBUTE_TUPLE`/`C_PRIMITIVE_TUPLE` are
    AOM2-only (`AOM2/master04.5-…class_definitions.adoc`). Any OPT 1.4
    validator therefore cannot rely on generic tuple semantics.
11. **Occurrences on single-valued attributes loosely specified:** "It only
    has significance for objects which are children of a container
    attribute… However, **it is not illegal.**"
    (`ADL1.4/master05-cadl.adoc` line 284) — the interaction with existence
    when both are stated on a single-valued attribute is not pinned down.
12. **Cardinality-vs-RM enforcement hedged:** "In theory, none of these
    constraints can be stronger than the semantics of the corresponding
    container in the relevant part of the reference model. However, in
    practice, developers often use lists… How such constraints are evaluated
    in practice may depend somewhat on knowledge of the software system."
    (`ADL1.4/master05-cadl.adoc` line 268.)
