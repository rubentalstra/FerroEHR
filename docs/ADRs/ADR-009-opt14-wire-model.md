# ADR-009: `opt14` stays a separate OPT-XML wire model beside `am14` (deliberate, guarded duplication)

- **Status:** accepted
- **Date:** 2026-07-06

## Context

The AOM 1.4 constraint model exists twice in the workspace:

1. **`openehr-am::am14`** — generated from the AOM 1.4 **BMM** (ADR-004): the
   canonical logical model with `#[derive(OpenEhrType)]` canonical-JSON
   (de)serialization, `openehr_base::Interval<T>` multiplicities, and the BMM
   `openehr_archetype_profile` domain types (`C_CODED_TEXT`, `C_ORDINAL`,
   `C_QUANTITY`).
2. **`openehr-its::opt14`** — generated by `emit-opt` (ADR-005) from the
   **Ocean OPT-XML XSD closure** (`Template.xsd` → `OpenehrProfile.xsd` →
   `Archetype.xsd` → `Resource.xsd`, vendored at
   `crates/openehr-its/schemas/xml/components/AM/Release-1.4/`): the typed
   model + `ToXml`/`FromXml` codec for `.opt` operational-template documents,
   which is what template upload (ITS-REST DEFINITION adl1.4) actually
   receives and what the WebTemplate builder consumes.

Spec-audit finding **F-09-02** (`docs/spec-audit/findings/09-templates-opt14.md`)
flagged this as a maintainability hazard: two parallel `C_*` trees can silently
drift, and the emitter header only documented the resource-metadata divergence.
The forcing question: should `emit-opt` resolve the shared constraint types to
`openehr_am::am14` (the way it already resolves RM leaves to
`openehr_rm`/`openehr_base`), leaving `opt14` as just the template envelope +
XML wire impls — or are the two models genuinely different shapes that must
both exist?

A field-by-field comparison (2026-07-06, W3-D) of the core constraint classes
answered it. The XSD wire model and the BMM logical model diverge structurally,
not cosmetically:

| Axis | `am14` (BMM/AOM 1.4) | `opt14` (OPT-XML XSD) |
|---|---|---|
| Domain-type set | `C_CODED_TEXT`, `C_ORDINAL`, `C_QUANTITY` | `C_CODE_PHRASE`, `C_CODE_REFERENCE`, `C_DV_ORDINAL`, `C_DV_QUANTITY`, `C_DV_STATE` (+ `STATE_MACHINE`/`STATE`/`TRANSITION`) — different names **and** different members; `C_DV_STATE`/`C_CODE_REFERENCE` have no BMM counterpart |
| `assumed_value` | `Any` → monomorphized `serde_json::Value` on every `C_DEFINED_OBJECT` descendant | typed per class (`Option<DvQuantity>`, `Option<DvOrdinal>`, `Option<DvState>`, `Option<CodePhrase>`, primitive options on `C_PRIMITIVE`s) |
| Ordinal lists | `C_ORDINAL.list: Vec<ORDINAL>` (constraint type: `symbol: CODE_PHRASE` + `value: i32`) | `C_DV_ORDINAL.list: Vec<DV_ORDINAL>` (the RM data type) |
| Quantity | `C_QUANTITY.property: String`; `C_QUANTITY_ITEM { magnitude: Interval<f64>, units: Option<String> }` | `C_DV_QUANTITY.property: Option<CODE_PHRASE>`; `C_QUANTITY_ITEM { magnitude: Option<IntervalOfReal>, precision: Option<IntervalOfInteger>, units: String }` |
| Coded text | `C_CODED_TEXT { terminology: String, code_list: Option<Vec<String>>, reference: Option<String> }` | `C_CODE_PHRASE { terminology_id: Option<TERMINOLOGY_ID>, code_list: Vec<String>, assumed_value: Option<CODE_PHRASE> }` |
| Multiplicities | `openehr_base::Interval<i32>` / `Interval<f64>` | the XSD `IntervalOfInteger`/`IntervalOfReal`/`IntervalOfDate*`/`IntervalOfDuration` shapes (explicit `lower_included`/`lower_unbounded`/… element sequence) |
| `C_PRIMITIVE_OBJECT.item` | mandatory `CPrimitive` | `Option<Box<CPrimitive>>` (real exports omit it) |
| Envelope | none of: | `OPERATIONAL_TEMPLATE`, `C_ARCHETYPE_ROOT`, `T_CONSTRAINT`/`T_ATTRIBUTE`/`T_COMPLEX_OBJECT` (default-value overlays), `FLAT_ARCHETYPE_ONTOLOGY` — OPT-only types the AOM 1.4 BMM does not define |
| Wire codec | canonical JSON (`_type` self-tagging) | canonical XML (`xsi:type` dispatch, XSD element order, attribute/element split) |

Constraints binding the decision: the vendored XSD is the authority for OPT
documents (the corpus and real-world exports follow it, including
XSD-vs-BMM optionality skews the emitter already handles leniently); ADR-004/005
forbid hand-editing generated code; the owner's bar is "no unjustified
duplication, no lossy shortcuts".

## Decision

1. **`opt14` remains a standalone, XSD-shaped OPT-XML wire adapter**; its
   `C_*` constraint types are **not** resolved to `openehr_am::am14`. The
   duplication is deliberate: the two generators serialize two genuinely
   different published shapes of the same abstract model (BMM logical vs
   Ocean OPT-XML wire), and forcing one Rust type set to serve both would
   require lossy mapping on every divergent axis above.
2. **The duplication is scoped and documented at the source**: the `emit_opt.rs`
   module header carries the full rationale + the divergence summary (PORT
   NOTE), so the next reader of either model finds this ADR.
3. **A drift guard is added**:
   `crates/openehr-its/tests/opt14_am14_divergence.rs` pins both models'
   constraint-type inventories with exhaustive (wildcard-free) matches plus an
   explicit list of the documented asymmetry. A spec/XSD bump that regenerates
   either side with a new, removed, or renamed constraint type fails the build
   until this sentinel and this ADR are consciously updated together.
4. **Losslessness of the wire adapter is asserted, not assumed**: the corpus
   gate gains a parse → `ToXml` → re-parse structural-equality round-trip over
   all 91 vendored `.opt` files plus a document-order assertion for
   `StringDictionaryItem` groups (which moved from `BTreeMap` to an
   order-preserving `IndexMap`, per the XSD's ordered sequence), and the
   previously-opaque `T_CONSTRAINT` (`default_value` overlays) is now generated
   and parsed (`T_VIEW`, an anonymous-inline presentation block, remains the
   single documented opaque type).

## Consequences

- **Easier:** each model serves its wire format with zero translation —
  `opt14` parses/serializes real OPT exports byte-faithfully-enough to
  round-trip the whole corpus; `am14` stays the canonical-JSON AOM. Consumers
  (WebTemplate builder, template service) keep a stable typed surface.
  Template `default_value` overlays are now available to FLAT default
  population instead of being dropped.
- **Harder, honestly:** two models of one abstract spec remain; anyone writing
  constraint-walking logic must pick the right one (rule of thumb: touching
  `.opt` XML or WebTemplate ⇒ `opt14`; canonical-JSON AOM / ADL ⇒ `am14`).
  A future AOM 1.4 spec bump costs two regenerations plus a sentinel/ADR
  review — that cost is the drift guard working as intended, not overhead to
  optimize away.
- The `opt14` serde-JSON derives remain non-canonical (externally-tagged, no
  `_type`) — a known scope boundary (hygiene note in findings 09); `opt14`
  JSON is not a wire format anywhere.
- If a consumer ever needs to cross the models (e.g. render an `opt14`
  constraint tree as canonical AOM JSON), that is a hand-written, tested
  mapping layer — not a reason to merge the generated models.

## Alternatives considered

- **Consolidate: resolve `opt14`'s shared `C_*` types to `openehr_am::am14`**
  (the F-09-02 "fix" candidate). Rejected on the field evidence above: the
  domain-type sets do not even align by name (`C_DV_STATE`, `C_CODE_REFERENCE`
  have no BMM counterpart; typed vs `Value` assumed values; `ORDINAL` vs
  `DV_ORDINAL` lists; different Interval shapes). Consolidation would force
  either lossy narrowing of the XML wire (rejected: lossy shortcut) or
  widening/hand-editing the BMM-generated `am14` away from its spec source
  (rejected: violates ADR-004's determinism).
- **Generate the XML codec for `am14` types directly** (one type set, two
  codecs). Rejected: the XSD's element order, attribute/element split, and
  `xsi:type` slots are defined against the *XSD* type shapes; emitting them
  over BMM-shaped types means synthesizing wire structure the BMM does not
  encode — exactly the mismatch (typed assumed values, IntervalOf\* elements,
  `C_DV_*` names) that makes the models different in the first place.
- **Keep both with no guard** (status quo ante). Rejected: silent drift on a
  spec bump is the real hazard F-09-02 identified; an inventory sentinel is
  cheap and forces the reconciliation conversation at the right moment.
- **Hand-write a lossless `opt14 → am14` converter now.** Rejected as
  speculative: no current consumer needs cross-model conversion (WebTemplate
  consumes `opt14` directly; nothing consumes `am14` constraint trees yet);
  building it before a consumer exists is dead code with a maintenance tail.
