## Method note

A `// @generated` Rust struct/enum existing proves nothing; these requirements are the *runtime wire contract* the write path (deserialization/validation) and serialization path must honour. The systemic question for Phase 2: does `#[derive(OpenEhrType)]` **reject a wrong `_type`** in every context (top-level, struct-typed slot, enum/abstract slot) and **emit `_type`** exactly where the schemas require a `const`?

## Systemic checks for Phase 2 (verification targets)

1. **Monomorphic-slot strictness beyond `subject` (R5–R9):** confirm each direct-`$ref` slot's *actual write path* deserializes through the concrete generated type so a foreign `_type` is rejected (the B1/B2 fix covered `EHR_STATUS.subject` only). Highest concern: `COMPOSITION.category` (R6), `DV_ORDINAL.symbol` (R8), `CODE_PHRASE.terminology_id` (R9).
2. **`_type`-mandatory abstract slots (R10–R14):** confirm a missing `_type` in an abstract DATA_VALUE/PARTY_PROXY/CONTENT_ITEM/ITEM_STRUCTURE slot is rejected (untagged-enum deserialization can silently pick a default).
3. **`_type`-optional slots with defaults (R15/R16):** confirm `name`/`hyperlink` accept an absent `_type` (default DV_TEXT/DV_URI) — over-strict rejection here is a conformance regression.
4. **Number typing (R17–R20):** confirm DV_COUNT.magnitude serializes as an integer (`3`, not `3.0`) and DV_QUANTITY.magnitude serializes as a real, per the split.
5. **`additionalProperties:false` (R3) + null omission (R39):** confirm unknown keys are rejected and unset optionals are omitted (not `null`).
