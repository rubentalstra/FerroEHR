> **Audit lens (chapter notes):** the terminology component defines the *reference data* (code sets + vocabulary groups) plus the *access duties* (`has_code`, `has_code_for_group_id`, `valid_code_set_id`, `valid_terminology_group_id`). The high-value requirements are the **membership-check rejection duties**: for each coded attribute the RM ties to a named group/code set via an `Xxx_valid` invariant (master05 §"Terms and Codes in the openEHR Reference Model"), composition / status / version / audit validation MUST reject any code not in the corresponding group/code set. The group- and code-set-identifier classes enumerate the *complete mandatory set* the validator must consult; the vocabulary/codeset files give the *exact allowed memberships* (a leniency risk if the stored membership drifts from these).
