### D1 — phantom `schedule/directory/REQUIREMENTS.md` citations (known systemic issue; 6 binding files, 0 case files)
No case YAML in `schedule/directory/` references the file, but six of the ten `bindings/its-rest/I_EHR_DIRECTORY.*.yaml` bindings cite `schedule/directory/REQUIREMENTS.md` — a file that never existed — as the adjudication anchor for the boolean-by-outcome-kind realization and the AMB-25/AMB-26 proposals:
- `I_EHR_DIRECTORY.has_directory.yaml` (line 8), `has_path.yaml` (line 8), `has_directory_version.yaml` (line 7) — "the boolean is carried by the ok/not_found outcome kind (schedule/directory/REQUIREMENTS.md)"
- `I_EHR_DIRECTORY.create_directory.yaml` (line 29) — "the AMB-25 proposal (schedule/directory/REQUIREMENTS.md)"
- `I_EHR_DIRECTORY.update_directory.yaml` (line 30), `delete_directory.yaml` (line 23) — "the AMB-26 proposal (schedule/directory/REQUIREMENTS.md)"

Proposed fix: replace each phantom pointer with the real anchors — the register ids (AMB-25/AMB-26) which exist and carry the adjudication, and for the boolean realization either a register entry or the OAS operation citation already present in the same comment block.

### D2 — `has_path-folder_structure` + the directory fixtures deviate from the official reference structure without an in-case adjudication
What the YAML says: "The 12 probes are the schedule's `$path`/`$result` data set, **verbatim**."
What the spec says (master09 §has_path-folder_structure data set, exact cells): `'/emergency/episode-x'`, `'/emergency/episode-x/summary-composition-x'`, `'/emergency/episode-y/summary-composition-y'`, `'/hospitalization/summary-composition-z'`; and §has_path-ehr_root_directory NOTE: "`'/'` represents the string slash, which is the default name for the root `FOLDER` at `EHR.directory`".
What the catalogue does: probes `/emergency/episode_x`, `/emergency/episode_x/summary_compo_x`, etc.; the provisioned fixture `corpus/fixtures/directory/reference_structure.json` names its root FOLDER `root` (not `/`), uses the underscore names, and adds an extra folder `foldername-w-special-chars` absent from the official structure. The names trace to the vendored Robot corpus (`CNF/tests/platform/robot/_resources/test_data_sets/directory/subfolders_in_directory.json` uses `episode_x`; the official Robot `has_path-folder_structure.robot` itself probes `/emergency/episode_x`), and `corpus/MANIFEST.yaml` carries a TODO ("replace the placeholder FOLDER payloads with spec-authored canonical FOLDER structures", #202) — so provenance exists, but the case claims verbatim fidelity it does not have, and the deviation carries no adjudication in the case.
Functional impact: none observed — probes and fixture are mutually consistent and the official true/false pattern (8 true, 4 false: full paths, partial paths, random) is fully preserved.
Proposed fix (either): (a) rename the fixture folders to the official master09 names (`episode-x`, `summary-composition-x`, …) and update the probes — the master09 table, not the Robot suite, is the oracle; or (b) keep the Robot-corpus names and replace the "verbatim" claim with an explicit adjudication note citing the Robot fixture provenance + the MANIFEST #202 TODO. Also decide/document the root-FOLDER-name question ('/'-as-root vs a root named `root`) in the same pass.

### D3 — ambiguity-tagging inconsistency vs the catalogue's own convention
The ehr chapter tags binding-level code-assignment ambiguities on the affected cases (`create_ehr-invalid_status` → `ambiguities: [AMB-2]`; `clear_ehr_modifiable-existing_ehr` → `[AMB-3]`), and the directory chapter itself tags AMB-8 on four cases. But: `create_directory-ehr_with_directory` (relies on AMB-25 for the 409), `update_directory-empty_ehr` + `delete_directory-empty_ehr` (rely on AMB-26 for the 404), and the six cases realizing preceding_version_uid as If-Match (AMB-3: `update_directory-ehr_with_directory`, `get_directory_at_time-ehr_with_directory_versions{,_empty_time}`, `get_directory_at_time-multiple_versions_first`, `has_directory_version-directory_with_two_versions`, `get_directory_at_version-directory_with_two_versions`, `get_versioned_directory-directory_with_two_versions`) reference the register only in comments, with no `ambiguities:` field (schema.rs supports it). Proposed fix: add the tags, matching the ehr-chapter convention, so register coverage is machine-visible.

### D4 — AMB-8 register handling only half-realized in the catalogue
The register (read in full) says: disposition `option_select`, handling "Sibling cases with option tags; the ICS declares the behaviour", `options: [directory-empty-structure, directory-empty-error]` — and the register schema requires ≥2 options for option_select. The catalogue contains ONLY `directory-empty-error` cases (grep over the whole artifact tree: no case anywhere carries `option: directory-empty-structure`). A party whose ICS declared `directory-empty-structure` would silently lose all F.1/G.1/G.2/L.1 coverage. Meanwhile the `get_directory` binding comment asserts a FIXED resolution ("the empty-vs-error question of AMB-8 resolves to the error branch on ITS-REST (no 200 empty-structure body exists for a missing directory)") — which contradicts the register's option_select disposition. The ITS-REST reasoning is sound (OAS 200_FOLDER_retrieved has no empty-structure representation for a never-created directory; the 404_directory... response explicitly covers the absent case), but the register does not record it.
Proposed fix (either): (a) re-word AMB-8's handling to record that on ITS-REST 1.1.0 only the error option is realizable (fixed by the binding, option retained for future ITSes); or (b) author the `directory-empty-structure` siblings so the register's promised sibling pair actually exists (they would verdict not-applicable on this ITS).

### D5 — `get_directory_at_time-ehr_with_directory_versions` step 3 pins the AMB-8 branch untagged, and probes a different instant than the official cell
What the YAML does: step 3 probes `${time:before(t0)}` (before the FIRST DIRECTORY COMMIT) and expects `not_found`, comment "(AMB-8 error branch on REST)" — but the case carries no `ambiguities: [AMB-8]` and no `option: directory-empty-error`, unlike the three sibling cases pinning the same branch; and no OAS citation in spec_refs.
What the spec says: master09 G.5 flow: "Invoke the get directory at time service for the `ehr_id` and a time before `EHR.time_created`. The service should return an empty structure." (official expectation = empty structure, official instant = before EHR creation). On ITS-REST the 404 is directly derivable: OAS `404_directory_unknown_ehr_id_or_no_version_at_time_or_no_path` — "when a directory does not exist at the specified `version_at_time`".
Impact: if an ICS ever declared the structure option (see D4), this untagged case would still hard-gate the error branch. The before(t0)-vs-before(time_created) instant difference is semantically equivalent for the outcome (no version extant either way) but is a silent ground deviation.
Proposed fix: add `ambiguities: [AMB-8]` + the option tag (or, better, cite the OAS 404 response in spec_refs as the fixed-wire derivation, consistent with whichever way D4 resolves), and note the instant substitution in the case comment.

## Ambiguities

### A1 — `update_directory-empty_ehr` + `delete_directory-empty_ehr`: supplied-stale-If-Match vs the missing-directory 404 is under-adjudicated, and the case comments contradict their own flows
What the YAMLs do: both flows send a synthetic `preceding_version_uid: "11111111-…::cnf.fake::1"` (rendered as `If-Match` by the binding) and expect `not_found` (404). Both case comments claim the opposite: "no preceding version exists so **no If-Match is sent**".
What the spec says, exact quotes:
- ITS-REST overview `Requests_and_responses.md` §If-Match: "If a service receives this header, and the condition evaluates to `false`, it MUST NOT perform the requested method. Instead, it MUST respond with HTTP status code `412 Precondition Failed`" — and for the omission alternative: "When the service expects `If-Match` for an operation, but the client does not provide it, the service SHOULD respond with `400 Bad Request`."
- OAS `412_directory`: "returned when `If-Match` request header doesn't match the latest version on the service side" (presupposes a latest version exists).
- OAS `404_unknown_ehr_id` + register AMB-26: "Bind not_found -> 404 for the missing-directory precondition; kind distinguished by the case's provisioned state."
The tension: with no directory, a received non-matching If-Match arguably "evaluates to false" → the overview's MUST-412; alternatively the missing-resource check precedes precondition evaluation → AMB-26's 404. Both readings are live in the wild: EHRbase Java answered `precondition_failed` (412) on exactly these two cases (`docs/conformance/COMPARISON.md` rows for update/delete_directory-empty_ehr). AMB-26 adjudicates only the 404-code overload, not this interaction, so the catalogue is currently resolving a genuine spec tension privately (and its own comments mis-describe the wire it sends).
Proposed fix: (1) fix the two case comments (the If-Match IS sent — the OAS marks the header `required: true`, which is why omission was not chosen); (2) extend AMB-26 (or add a new register entry) to adjudicate the supplied-stale-If-Match-on-missing-directory precedence explicitly, with the two quotes above as the recorded tension and the chosen normative handling (404, or accept {404, 412}); (3) add `ambiguities:` tags on both cases.
