## Defects

**D1 — two_commits_second_creation: wrong OPT provisioned (blocking).**
YAML: `requires.templates: [cnf.opt.minimal_event]` with `data_sets: [cnf.composition.persistent.v1, cnf.composition.persistent.v2]`. MANIFEST (`cnf.composition.persistent.v1/.v2`) and the fixtures themselves declare `template_id: persistent_minimal.en.v1`; that template lives only in `templates/minimal_persistent.opt` (`<template_id><value>persistent_minimal.en.v1</value>` verified) = corpus key `cnf.opt.minimal_persistent`. Step 1 expects `created` but commits against an unprovisioned OPT — on a conformant SUT the case can only fail with the missing-template rejection, misreporting the SUT. Official C.9 ("Commit two CONTRIBUTIONa on same COMPOSITION with second having change_type = creation" + the persistent-composition validity NOTE) requires the first commit to succeed. Fix: `templates: [cnf.opt.minimal_persistent]`.

**D3 — AMB-3 misapplied to the contribution wire (8 cases).**
Cases tagged `ambiguities: [AMB-3]` and/or commented "ITS-REST: If-Match (AMB-3)": `-delete`, `-event_composition`, `-persistent_composition`, `-two_commits_second_creation`, `-two_commits_second_invalid`, `-minimal_ehr_status`, `-full_ehr_status`, `-update_existing_directory`. AMB-3's ambiguity is "The SM does not say where preceding_version_uid lives for update … the ITS-REST binding realizes it as If-Match" — that is the COMPOSITION-update endpoint. For `commit_contribution` there is no silence and no If-Match: the SM `update_version.adoc` defines `preceding_version_uid: OBJECT_VERSION_ID` on UPDATE_VERSION itself ("Current version in service for which this version is an update"), the OAS `UpdateVersion` schema carries the same property, and the runner's envelope builder (`exec/driver.rs` 811–825) inserts it into the version member body; the `I_EHR_CONTRIBUTION.commit_contribution` binding sends only `Prefer`, never If-Match. Fix: drop the AMB-3 tags/comments on these 8 cases and cite `SM update_version.adoc` / OAS `UpdateVersion.preceding_version_uid` instead.

**D4 — full_ehr_status: official precondition not realized.**
Official D.2 precondition 2: "The EHR contains a full `EHR_STATUS` (all the optional information is set, i.e. `subject.external_ref` etc)". The case's `requires: ehr: { commits: none }` can only mint an EHR with the DEFAULT status (`model/case.rs`: `requires.ehr` is `none | { commits: none|any }`, nothing else), and the comment's claim "EHR with a full EHR_STATUS; mints ${ehr_id}" is unfulfillable. The catalogue instead commits the full status AS the tested modification — the official distinguishing axis (starting state full vs default) is lost, unregistered. Fix: establish the full status first (an explicit flow step committing `cnf.ehr_status.with_subject.alt` as modification, then the tested modification on top — the master08 scenario 3 "modifications already done" reading), or register the D.2 title-vs-precondition muddle as an editorial ambiguity and say which reading the catalogue takes.

**D5 — D.1/D.2 official verification step dropped (minimal_ehr_status, full_ehr_status).**
Official flow step 3 (both cases): "Verify expected `CONTRIBUTION` uids and `CONTRIBUTION` count for the EHR with `ehr_id`". Neither case captures `created.contribution_uid` nor performs any verification. The uid half is realizable on ITS-REST 1.1.0 (capture + `get_contribution`); the count half is unrealized (`contribution_count` — AMB-33; `list_contributions` — AMB-22) and its omission needs the machine-readable tag. Fix: add the capture + GET step; tag the count omission.

**D6 — non_exiting_opt: stale, self-contradicting comment + ghost references.**
The header comment states "the commit_contribution binding (unmodifiable) wires only 201/400/404/409 and does not distinctly map template_not_found, so the missing-OPT reject realizes as validation_failed" while the case expects `template_not_found` and the binding DOES map `template_not_found` distinctly (400, `alt_status: [422]`, AMB-40). Two references to a `REQUIREMENTS.md` that does not exist under `schedule/contribution/`. Fix: rewrite the comment to the current binding reality (kind distinguished by fixture, AMB-40/AMB-2 pattern); scrub the ghosts.

**D7 — two_commits_second_creation: self-contradicting rejection rationale.**
Header comment: "the rejected outcome is a versioning-state conflict (409 conflict) — … `already_exists` is not wired distinctly by the commit_contribution binding (see REQUIREMENTS.md)"; the case expects `validation_failed` (400) with the sound `400_CONTRIBUTION` mismatched-modification-type derivation on the expect line. One of the two rationales must go (the 400 one is derivable; 409 is not enumerated for this shape); scrub the ghost reference.

**D8 — valid_composition: official version-id cell unasserted.**
Official C.1 post-condition: "the version ID matches the `change_type` executed (creation = 1, modification/amendment = 2, 3, …)". The case asserts `change_type: CREATE` only; the assertion vocabulary's `uid_pattern` (`"…::<system>::1"` — used elsewhere in the catalogue) encodes the cell exactly. The "EHR has a new CONTRIBUTION" post-condition is prose `assert: state` with no `verified_by`. Fix: add `uid_pattern` to the version assert; add `verified_by: I_EHR_CONTRIBUTION.get_contribution-existing` (or an in-flow GET). Same-family note (not defected): C.5/C.6/C.7's "same OBJECT_VERSION_ID with version number = 2" cells rest on the count-2 versioned-object read; `uid_pattern: "…::<system>::2"` would pin them.

**D9 — `commit:` preconditions never provision (get/has bad_contribution; latent in list post_commit).**
`requires.commit: [cnf.composition.minimal_event.v1]` names a single-object corpus entry, but `provision_commit_sets` (`tools/cnf-runner/src/exec/driver.rs` 951–998) iterates only `set.as_array()` and SILENTLY skips non-arrays — the official precondition "The EHR has `CONTRIBUTIONs`" (G.4/H.4) is never established; the cases still pass because the probed uid is absent either way, but they no longer test the populated-EHR ground the schedule specifies. Attribution: catalogue (wrong key kind for the bulk-set vocabulary) + **runner machinery** (a skipped provisioning step must be a hard error, never silence). Fix: wrap the singles as one-element sets (or teach the provisioner single-object sets) AND make the runner fail loud on an unprovisionable `commit:` key.

**D10 — AMB-23 exists but is machine-referenced nowhere (4 has_* cases + binding).**
Register entry AMB-23 covers precisely the Boolean→GET-200/404 realization of `has_contribution`, yet no case carries `ambiguities: [AMB-23]` and the binding's comment cites the nonexistent `REQUIREMENTS.md` as an "ambiguity candidate" — stale (the entry is registered) and prose-only. The AMB-17/AMB-33 convention (unrealized/diverging realizations tagged at case level — verified in definition_adl14 and admin chapters) applies. Fix: `ambiguities: [AMB-23]` on `has_contribution-existing/-empty_ehr/-bad_ehr/-bad_contribution`; point the binding comment at AMB-23.

**D11 — AMB-22 untagged on the five list_contributions cases.**
The binding's `unrealized.ambiguity: AMB-22` is correct and machine-readable, but the five cases cite AMB-22 in comments only — no `ambiguities: [AMB-22]` tag (the AMB-17 delete_opt cases all carry the tag). The binding comment also calls AMB-22 "proposed" and points at `schedule/contribution/REQUIREMENTS.md` (nonexistent) — stale. Fix: tag the five cases; refresh the binding comment.

**D12 — list_contributions-ehr_containing_ehr_status: unprovisionable precondition (latent).**
`commit: [cnf.ehr_status.minimal]` — the commit provisioning path drives every set through the `I_EHR_COMPOSITION.create_composition` binding (`exec/driver.rs` 961), which cannot commit an EHR_STATUS (the status wire is the PUT with a preceding target, or a contribution with `change_type: modification`). Harmless today (the case is N/A under AMB-22) but wrong the day a later ITS realizes the wire. Fix: an explicit flow/provisioning step through the status modification path (the minimal_ehr_status pattern).

**A1 — AMBIGUITY (register entry needed): data-less delete member — RM vs OAS.**
RM `common/master06-change_control_package.adoc` §2.4: "deletion of existing item: a new `ORIGINAL_VERSION` whose data attribute is set to Void … `change_type` is set to the code `523|deleted|`"; `original_version.adoc`: `data` 0..1. The OAS `UpdateVersion` schema: `required: [lifecycle_state, data, commit_audit]` — a delete member WITHOUT `data` violates the wire schema the SUT may enforce, and the official C.7 flow cell ("The `COMPOSITION` should reference the same `template_id`") reads as a data-carrying member. The catalogue (cases `-delete`, `-ehr_status_invalid_change_type_deleted`; runner envelope builder `exec/driver.rs` 776–808) adopts the RM Void-data reading with no register entry. Needs an `ambiguities.yaml` entry (typed disposition, both citations quoted) + tags on the two cases; SPECPR candidate (relax `UpdateVersion.required` for the deletion case or define the delete-member wire shape).

**A2 — AMBIGUITY (register entry needed): status code for the cannot-delete-EHR_STATUS rejection.**
master08 reject case 1: the EHR_STATUS "can't be deleted once created". `contribution_create` enumerates 201/400/404/409; the generic `409` text covers only "a resource with same identifier(s) already exists" — no sentence assigns the cannot-delete state-conflict, and `400_CONTRIBUTION` scopes parse/mismatch failures. The case asserts `conflict` (409) exactly, underivably. Needs an AMB-21/25/26-style entry (state-conflict family → 409, flag for upstream code assignment) + the tag on `-ehr_status_invalid_change_type_deleted`.
