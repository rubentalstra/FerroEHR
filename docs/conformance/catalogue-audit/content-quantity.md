## Defects

### D1 — CONT-DV_SCALE-validate_constraint: violates labels contradict the schedule cell and the case's own description
- YAML says: `violates: ["constraint(C_DV_ORDINAL.list): no matching value"]` / `…no matching symbol` while `description:` and the template comment say `C_DV_SCALE.list`.
- Spec says: master17.3 §CONT-DV_SCALE-validate_constraint table, "constraints violated" column: "`C_DV_SCALE.list: no matching value`" and "`C_DV_SCALE.list: no matching symbol`" (lines 71–72 of `docs/specs/openehr/CNF/docs/platform_test_schedule/master17.3-content_tc_data_types-quantity.adoc`). (Contrast: the DV_INTERVAL\<DV_SCALE\> constraint table at §CONT-DV_INTERVAL_DV_SCALE-validate_constraint genuinely uses `C_DV_ORDINAL.list` headers — the plain DV_SCALE case does not.)
- Fix: relabel both violates entries `constraint(C_DV_SCALE.list): …` to match the schedule cell (behaviourally inert — the labels are informational — but the current text contradicts the case itself).

### D2 — mixed-precision comparability rows assert a gating `accepted` outside every register entry (CONT-DV_INTERVAL_DV_DATE-validate_open row 7; CONT-DV_INTERVAL_DV_TIME-validate_open row 7)
- YAML says: `["2021", "2021-10", false, false, true, true, accepted, []]` and `["10", "10:45:00", …, accepted, []]`.
- Spec says: the schedule rows carry "IMO two dates/times with different components … shouldn't be strictly comparable" with verdict rejected (master17.3 lines 657, 734). The RM answers the comparability half — `dv_date.adoc` / `dv_time.adoc` `is_strictly_comparable_to`: "True, for any two Dates." / "True, for any two Times." — but the then-applicable `Limits_consistent` (`lower <= upper`, BASE `interval.adoc` §Invariants) orders by `magnitude()`, whose value for partial dates/times is exactly the SPECPR-380 openness the register already governs: AMB-29 ("verdicts on mixed-precision comparisons are reported but excluded from profile computation until SPECPR-380 resolves", report_only) and AMB-27 ("the forum-note rows keep the stated verdict with the note kept as case commentary").
- The flip to `accepted` as a *gating* expectation follows neither register handling and cites no register entry — a private resolution of a registered ambiguity.
- Fix: tag both cases `ambiguities: [AMB-29]` and give these rows the report_only treatment AMB-29 prescribes (or, if the adjudication is that any consistent partial-magnitude reading orders these particular pairs identically, extend AMB-29's text to say so explicitly and cite it from the rows).

### D3 — AMB-43-adjudicated rows carry no machine-readable register linkage (7 cases)
- Affected: CONT-DV_INTERVAL_DV_DATE-validate_open, CONT-DV_INTERVAL_DV_DATE_TIME-validate_open, CONT-DV_INTERVAL_DV_TIME-validate_open (no AMB-43 mention at all, prose headers only); CONT-DV_INTERVAL_DV_DURATION-validate_open, CONT-DV_INTERVAL_DV_ORDINAL-validate_open, CONT-DV_INTERVAL_DV_SCALE-validate_open (comment-only `# AMB-43`).
- The case-core schema defines `ambiguities: ["^AMB-[0-9]+$"]` and other chapters (admin, demographic, security) use it; AMB-43's handling says "The affected content rows expect accepted with this citation" — a YAML comment is not a citation the verdict pipeline or a reviewer can machine-trace, and three of the six carry no reference at all.
- Fix: add `ambiguities: [AMB-43]` to all six open-interval cases (plus AMB-29 per D2 where applicable). Verdicts themselves are correct per the standing adjudication — no expectation change.

### D4 — CONT-DV_INTERVAL_DV_TIME-validate_lower_upper_range row 8: schedule-verdict override not registered

Same entry should also cover the row-9 accepted/"C_TIME.range (upper)" contradiction cell this case resolves via the AMB-27 verdict-cell-wins rule.

## Ambiguities

### A1 — DV_TIME literal form: CNF's deliberate leading `T` vs BASE Iso8601_time syntax (3 cases)
- Affected: CONT-DV_INTERVAL_DV_TIME-validate_open, -validate_lower_upper_constraint, -validate_lower_upper_range (each carries the comment "time literals corrected 2026-07-22: … no leading T designator").
- CNF says: master17.4 §DV_TIME NOTE — "the time marker `T` can be ommitted for the extended format in ISO8601:2019 … Since this is nor mandatory, our test data sets all include the `T` time marker" (and the master17.3 interval-of-time tables print `T10`, `T11:00:00`, …).
- BASE says: `org.openehr.base.foundation_types.iso8601_time.adoc` §Description — value is "`hh:mm:ss[(,|.)sss][Z|±hh[:mm]]` (extended, preferred) or `hhmmss…` (compact)" — no leading `T` in either form.
- The catalogue's T-stripping follows the BASE class (the RM `DV_TIME.value` oracle) and is the defensible reading, but it is a CNF-schedule-vs-BASE divergence resolved in YAML comments; per the register discipline (a runner that resolves an ambiguity privately is non-conformant to the schedule) it belongs in `ambiguities.yaml` with a fixed_handling disposition ("time literals take the BASE Iso8601_time form; the schedule's T-prefixed data sets are transcribed without the marker") and `ambiguities:` tags on the three cases.
